# Script locks: decision for review

**Decision (2026-10-31): keep floating dependencies; the rollout is retired.** The owner does not want the upkeep of locks for a personal repository. A dependency that breaks a tool gets fixed when it is found. The earlier selective-lock choice is withdrawn, and the rest of this record is kept only as pilot history.

## Pilot evidence

On uv 0.13.6 and Homebrew Python 3.15.2, isolated Tax2 and Jtree sidecar locks were generated from unchanged launcher declarations. To distinguish lock use from coincidentally equal floating resolutions, Jtree's private copy was temporarily constrained to Uvicorn 0.34.3, locked, restored to its original unpinned declaration, and relocked without upgrade. The valid restored-header lock retained 0.34.3; the initial unconstrained resolution was 0.54.0. Actual `uv run --script --locked ... --help` used 0.34.3, but the current runner's `--with-requirements <script>` overlay installed 0.54.0. Thus this runner form did not honor the sidecar in this controlled case.

Exporting each script lock with `uv export --no-python-downloads --script <script> --frozen --format requirements.txt --no-hashes --output-file <private-file>` and using that export plus the project's test-only requirements gave matching versions for all shared runtime distributions in these pilots: Tax2 6 runtime distributions versus 14 test distributions, Jtree 14 versus 28. The additional distributions are test dependencies and their transitives; their versions are not locked by this procedure. All 432 Tax2 tests and 160 Jtree tests passed in that form, plus inventory and compatibility probes; Jtree emitted one Playwright fixture deprecation warning. Installed runtime distributions' `Requires-Python` metadata was checked against 3.15.2 through the matching test inventory; no incompatibility was found. This extra check matters because uv 0.13.6 ignores dependency `Requires-Python` upper bounds, including in `uv pip check`.

When the private Jtree header was changed to require Uvicorn 0.54.0 while its lock retained 0.34.3, `uv run --locked --script ... --help` exited 1 with a stale-lock error; `--frozen` exited 0 and used 0.34.3. Restore the declaration before normal use. A frozen export trusts the lock, so a separate freshness check is necessary before exporting. These are observed behaviors of the tested uv version, not a guarantee for other versions. A script lock does not pin the exact Python interpreter, browser binary, or test-only dependencies. The browser tests used cached Chromium revision 1248; no Python or browser was downloaded. Runtime invocations were source-inspected help paths, not live deployment acceptance.

## Scope and delivery

Candidates with third-party runtime dependencies in the guard's 34-launcher inventory are: EditDB, Jtree, Harscope, MLS Tracker, Docpipe, Storage Monitor, Tax2, RouterView, Expense Dock, Git Fleet, Launchmaster, Router Log Analyzer, HYSA Excel, ETF Monte Carlo, Benchmark, Cognitive Switchyard, Doc Linearizer, Data Format Converter, both Reversible Skew launchers, Video Scenes, both Apple Health extractors, and Transcription. This includes launchers outside the test registry. Existing direct pins still leave transitive dependencies floating. Git Fleet and RouterView remain in scope; their browser suites pass since `1886b33`. The remaining ten guard entries have empty dependency lists and gain little from package locks; their interpreter and other runtime requirements still need validation. Model Sentinel's builder is among these stdlib entries, while its installed zipapp has a separate runtime contract. Docker, non-uv tools, and other nonstandard delivery paths remain under their own policies.

Benchmark has a project `uv.lock`, but `bench` runs as a PEP 723 script. A project lock alone is not evidence that this script uses the same resolution. Treat its script and project delivery paths separately.

Today the deployment audit compares Jtree and several other installed commands as individual files; a sidecar needs an explicit copy and comparison mapping. Tax2's tracked project-copy procedure can include a tracked sidecar, but its deployment and audit must verify it and handle stale installed sidecars on rollback or removal. The test runner and deployed-test example currently consume launcher headers, not exported lock pins. A future rollout must update and validate these paths, including clean helper imports and installed-copy checks. No live deployment was performed by this investigation.

Git Fleet discovers PEP 723 declarations but does not read adjacent script locks. Its `uv.lock` version lookup applies to `pyproject.toml` and unique registry versions; its security view does not audit undeclared Python transitives. Consequently a script sidecar is not currently a complete vulnerability inventory. Exporting pins could provide an audit input, but the selected format, integrity/hash handling, platform markers, parser support, and security scanner coverage need explicit design and verification. The pilot deliberately used `--no-hashes`; that does not establish artifact integrity. Do not call an unverified export or dashboard scan a complete lock audit.

## Options and next steps

1. **Selective runtime locks (owner-selected):** lock candidates as they are validated, keeping stdlib and special-delivery exceptions explicit. This limits churn while improving reproducibility where dependencies matter, but requires per-project rollout, testing and deployment changes.
2. **Fleet locks:** lock all eligible scripts under a common process. This makes policy more uniform but increases review, refresh, storage and deployment work; empty locks do not pin Python or browsers.
3. **Keep floating:** preserve current simplicity and automatic uptake of compatible releases, accepting that later installs and tests may resolve different versions. Continue recording actual environments for releases.

For either locking option, establish ownership and cadence; on a private branch refresh a lock intentionally, review package, marker and platform changes, validate interpreter and dependency metadata, audit the complete selected pins, run the project's complete documented suites and acceptance gates, then update and verify the installed sidecar with its launcher. Test-only packages require their own reproducibility decision. Include rollback and stale-sidecar removal in the deployment design. Run a lock freshness check before export and compare actual runtime and test distributions on each supported target; lock contents alone do not prove installation or compatibility. Avoid routine upgrades without reviewing security fixes, and define an urgent advisory path.

For a pilot reproduction, create an isolated checkout and cache, inspect each launcher's help path, run `uv lock --no-python-downloads --script <launcher>` with authorization, then compare `uv pip freeze --python <actual-script-venv>/bin/python` with the suite environment. Use `uv run --no-project --isolated --no-python-downloads --python <approved-homebrew-python> --with-requirements <export> --with-requirements <test-file> python -m <documented-suite>` after sanitizing inherited Python and venv settings. Use only private synthetic state and the cached browser. These commands are an experiment description, not permission to change locks, install interpreters, download browsers, or deploy.
